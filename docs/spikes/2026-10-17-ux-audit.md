# Hutan usability audit: from parallel work to reviewed delivery

Date: 2026-10-17. Method: read-only repository/documentation inspection and primary-source web research. No app was launched, built, tested, or visually inspected; no installed application, user data, credentials, or agent configuration was touched. This report is the sole output file; it is not committed.

## 1. Scope, confidence, and executive finding

This is a **workflow and discoverability audit**, not an observed usability study. “Today” means the inspected main-checkout documentation and command registry, not a claim about the binary in `/Applications/Hutan.app`. User-reported friction is accepted as ground truth. Competitor behavior below is attributed to its published documentation, not independently exercised. `[INFERENCE]` marks inferred gaps, likely user effects, estimates, and recommendations; a missing mention in documentation is not proof that a feature is absent.

**Finding:** Hutan already has much of the hard substrate: daemon-owned sessions and approvals, structured multi-harness chat, explicit context, task dependencies, worktree isolation, a monitor, history, and guarded local merge. The main opportunity is to make that substrate feel like **one continuous, discoverable journey** rather than a collection of palette commands and panels. Rebuilding a full IDE or cloud platform is not a prerequisite.

The user's immediate requests map directly to K-1 (familiar keys and visible dock buttons), V-1 (modal text editing), R-1 (rich context everywhere), and M6-D (background daemon visibility). These remain **in-flight specifications**, not completed behavior in this audit. D-2 first-run setup is merged per the assignment and documented in the inspected design; do not propose another onboarding implementation.

### Evidence hierarchy and existing strengths

- [Command registry and default bindings](../../crates/desktop/src/workbench/actions.rs), specifically `commands` and `default_bindings`, are authoritative for the exact palette labels and keys quoted below.
- [Design](../design.md), [orchestration](../orchestration.md), [agents](../agents.md), and [assistant](../assistant.md) explain the surface. Where they conflict, this report calls it out rather than silently choosing a convenient account.
- [README](../../README.md) is the front door, but contains stale lifecycle/status statements. [Vision](../vision.md) describes targets, not delivery evidence.
- The daemon owning processes, journals, approvals, tasks, worktrees, and context reads is a valuable differentiator. Any proposed new stateful workflow belongs there; the desktop renders and submits decisions. Layout, focus, key routing, and vim mode remain client presentation concerns.
- Hutan already has an attention ladder: session → project/workspace → Needs you → status item → desktop menu bar / Dock / notifications; `⌘⇧J` reaches the next attention item. This is not a missing-feature audit finding.
- Hutan already has a Tasks panel and Changes view with merge and post-merge cleanup. “Add tasks/diffs/worktrees” would duplicate delivered work.

## 3. End-to-end journeys

All keys in this section are **the inspected pre-K-1 Hutan defaults**. In particular, `⌘J` currently opens Jump, not the bottom dock. K-1's proposed default changes that distinction.

### J1. Install, connect an agent, and complete the first useful task

**Comparables.** Zed asks the user to configure a model or external agent; Claude Code starts with environment/folder/model/permissions; Conductor guides creation of the first isolated workspace. Claude Desktop's `+` and quick-entry path support immediate non-coding usefulness. Sources: product rows above.

**Hutan today.** D-2's sheet runs Welcome → Look → Agents → Background → Command line → Done. Agents shows detection, harness-owned login/install flows, hook choices, and assistant backend; Background separates keep-running from start-at-login and asks notification permission only on action. Finish offers Open a folder and New terminal. Reopen with `⌘K` → **Hutan: Run Setup…** or Settings → app → **Run setup again**. `⌘O` opens a project; `⌘⇧T` → **Session: New Agent…** selects installed harness/model/folder; **Accounts…** and **Models: Manage Providers…** remain available. See [design: first-run setup](../design.md#first-run-setup-d-2).

**Friction / proposal [INFERENCE].** Setup is covered, not absent. Its success criterion should be “first reply / first task with a clear checkout,” not merely dismissing the sheet. Reuse its detected-account state and existing error recovery in later empty states; do not make returning users redo setup. The audit did not exercise installation, login, or first reply.

### J2. Start two independent agents on one repository without collisions

**Comparables.** Orca creates isolated worktrees and advertises prompt fan-out; Conductor makes one workspace per independently shippable unit; Codex and Zed put worktree selection near the conversation; Claude Code offers `claude --worktree feature-auth` in separate terminals.

**Hutan today.** `⌘O` chooses the repo. `⌘K` → **Tasks: New Task…** opens the right-dock form: title, prompt, Run (terminal/Codex/OMP/Claude), Where (main/new worktree), branch, After dependencies, and automatic start. Repeat for a second task; `hutan task add "Feature A" --ws <project> --worktree=feature/a --agent omp --prompt "..." --auto` has the same daemon-owned lifecycle. Automatic scheduling defaults to three concurrent tasks; manual starts ignore that limit. A terminal-first path is **Worktree: New Terminal in Worktree…**, then the agent CLI, or `hutan new --worktree feature/a --title A -- omp`. Session rows show `main` / `wt <branch>` and a shared-checkout warning when two reported agents share a checkout. Sources: [orchestration](../orchestration.md#tasks), [design: Tasks panel](../design.md#tasks-panel-m7-c).

**Friction / proposal [INFERENCE].** The direct New Agent path documents a folder but not the Tasks form's placement/dependency choices; the clearest isolated-agent launch is therefore hidden behind a different noun. Put **New task / Start agent** visibly in the project header, with explicit main/worktree placement, harness, prompt, and base branch. Reuse task creation and worktree APIs, not a second launcher model. Main checkout must remain an intentional option, never silently forbidden. Environment bootstrapping for fresh worktrees is not established by the inspected Hutan sources; label it as unknown rather than promise runnable dependencies.

### J3. Watch a fleet, find the blocked one, and return to deferred work

**Comparables.** Herdr surfaces working/blocked/idle; Orca's bell navigates to the right pane and permits marking unread; Zed groups threads by project; Conductor treats workspace streams as reviewable work.

**Hutan today.** Sidebar **Needs you** and workspace rollups; `⌘⇧J` (**Session: Jump to Next That Needs You**); `⌘⇧O` Overview; `⌘K` → **Agents: Show Monitor** / **Agents: Show Only Blocked**. Monitor chips select workspace/all, blocked, and finished; rows show state, activity, model, duration, usage when reported, and subagent tree. Clicking opens its session; a reported transcript can be revealed from its menu. Right dock also hosts Tasks; `⌘⌥R` toggles Resources. See [design: monitor](../design.md#agent-monitor-m13-b).

**Friction / proposal [INFERENCE].** The existing attention model is strong, but “observed” and “resolved” are different: visiting a failure clears its unread state, whereas the user may want to return later. A daemon-owned **mark unread / defer** flag and a stable attention list would preserve intentional follow-up across clients. Show the reason, project, and task beside each attention action; do not flatten every agent into an unexplained colored dot.

### J4. Answer an approval or a clarifying question, then continue safely

**Comparables.** Claude Code displays permission mode beside the prompt; Warp exposes per-profile autonomy and questions; Cursor documents questions during work. Hutan should preserve vendor policy rather than imply uniform sandbox guarantees.

**Hutan today.** Structured approval cards show only the provider's offered options; pending requests also appear in Inspector → Approvals, status, Needs you, and **Agent: Review Approvals…**. Empty composer keys `1`–`4` answer the oldest request per [agents](../agents.md#the-desktop-chat-view); the design also documents `⌘↩` / Escape when an approval card has focus. CLI: `hutan approvals`, then `hutan approve <id|prefix> <option>`. Decisions and answering-client provenance are journaled; approvals expire on turn end/process exit/daemon restart. Codex policy and ACP harness policy differ; unsupported policy settings are refused rather than faked. **Codex `requestUserInput` and MCP elicitation are explicitly declined**, not rendered as answerable questions ([agents: adapter](../agents.md#the-adapter), [limits](../agents.md#limits)).

**Friction / proposal [INFERENCE].** Approval coverage is not question coverage. Add daemon-owned typed pending questions (schema, options/free text, request/session identity, resolution/expiry), adapters that respond with the real provider shape, and a question card in the same attention path. Initially expose only genuinely supported backends. Make keyboard target/scope clear so a number typed for one task cannot accidentally decide another; the two focus-specific shortcut descriptions need reconciliation, not a blanket global approval key.

### J5. Ask a quick question with a failure, file, screenshot, or pasted text

**Comparables.** Warp attaches a failed command block directly; Zed adds selection, files, and images; Claude quick entry captures visual context from another app; Orca accepts file/image drops.

**Hutan today.** `⌘K` → **Assistant: Open / Focus**, with Global/Home or Workspace scope and backend/model chooser. No default in-app assistant key; an optional `assistant.global_shortcut` can summon it system-wide. `+ Attach` / `@shell`, `@agent` or `@omp`, `@file path:1-40`, and `@search query` create explicit context chips. Shell block hover → Send to agent, or **Block: Send to Agent**, targets the last-focused eligible chat/assistant or a picker. `⌘↑` / `⌘↓` navigate terminal blocks; `⌘⇧C` copies output. `hutan ask "Why did this fail?" --ws <project> --attach file:src/lib.rs` is the CLI route. Default send is `⌘↩`; Enter is newline unless `chat.send_on_enter` is enabled. Reads/redaction/budgets are daemon-side, with refusal preserving draft/chips. Sources: [assistant desktop](../assistant.md#desktop), [agents chat view](../agents.md#the-desktop-chat-view).

**Friction / proposal.** Current documented limits are text-only; Codex attachments are refused, while later ACP text attachment support is documented despite older blanket wording. **R-1 covers** file/image drop and paste, long-paste chips, explicit file picking, and backend-aware refusal in every chat; see §5. **[INFERENCE]** Make the recipient and Global versus Workspace scope visible before sending shell context. Surface a small “Explain failure” action that reuses attachment selection and the assistant, without reading adjacent sessions automatically. Rich input is not permission to send unselected files or switch backends silently.

### J6. Edit a substantial prompt without fighting the input

**Comparables.** Zed supports modal bindings and configurable contexts; its Agent Panel has an expandable message editor. Claude Desktop, Warp, and Orca make attachment affordances visible next to composing.

**Hutan today.** Composer is backed by [`TextInput`](../../crates/desktop/src/workbench/chat/input.rs): text/caret and editing operations. Default `⌘↩` send, Enter newline, `⌘.` interrupt. No vim mode is part of the inspected default surface; terminal-hosted vim/TUI bindings are a separate concern.

**Friction / proposal [INFERENCE].** **V-1 covers** reusable Insert/Normal/Visual editing, undo/redo, visible mode/caret, and live settings across text fields; it must not intercept PTY input. **R-1** covers long pastes and attachment chips. Keep send/newline/escape behavior explicit where vim, palette dismissal, and attachment removal intersect; do not describe this as embedding Zed's whole editor.

### J7. Review changes, request corrections, validate, and merge

**Comparables.** Orca, Conductor, Codex, and Claude Code let users attach diff comments to the agent conversation. Zed offers change review with hunk controls; Cursor adds checkpoints and dedicated review. Conductor carries the flow through checks, PR, merge, archive.

**Hutan today.** Task **Changes**, a session's placement/context menu **Review Changes…**, or `⌘K` → **Worktree: Review Changes…** opens **Changes · <branch>**. It shows merge-base comparison, files and `+/−`, **With uncommitted**, **Refresh**, read-only unified hunks, binary/truncation indicators; UI is capped at 500 lines per file. **Merge into main…** offers merge/squash/rebase and message, daemon refusals/conflict files remain visible, then **Remove worktree and branch** or **Keep**. CLI: `hutan wt diff <branch> [--base REF] [--committed] [--stat]`, `hutan wt merge <branch> [--into BRANCH] [--squash | --rebase] [-m MSG]`. Dirty main checkout and invalid target are refused; conflicts abort rather than leave an implicit conflict-resolution workspace. Fetch/push/PR creation and conflict resolution are explicitly outside these APIs ([orchestration: review](../orchestration.md#review-and-merge), [design: Changes](../design.md#changes-view)).

**Friction / proposal [INFERENCE].** Two separate issues matter:

1. Read-only diffs lack the documented competitors' line-comment → correction loop. Add **Ask agent about selection / Request changes**, anchored to checkout, base/head, file, hunk, and the selected task/session; journal feedback in the daemon. Use external-editor handoff before building an IDE.
2. The diff includes uncommitted changes, while ordinary branch merge integrates commits; `source_dirty` and the post-merge cleanup copy acknowledge remaining work. Clearly separate **what is displayed**, **what will merge**, and **what deletion would discard**. Never label the whole task integrated merely because branch merge succeeded. A task becomes `done` when a chat turn completes or an integrated agent goes idle; automatic dependants can then start. That is execution completion, not human acceptance or passing checks. Add an explicit daemon-owned review/acceptance facet and dependency policy if users need verified/reviewed gates, without silently changing existing task semantics.

### J8. Leave, close the app, restart, and know what survived

**Comparables.** Herdr provides the clearest survival matrix: detach keeps real processes, server restart reconstructs state, native agent resume is distinct, live handoff is experimental. Orca advertises restart-persistent scrollback. Claude cloud execution and Cursor cloud sandboxes are separate execution locations, not proof of local process survival.

**Hutan today.** `⌘W` / **Tab: Close (Detach)** detaches a tab; **Session: Stop…** / `⌘⇧W` is explicit stopping. Per design, **closing the last window defaults to quitting**, so it must not be described as invariably harmless window detach. Quit with live work offers Stop Sessions & Quit / Keep Running in Background / Cancel unless background settings already allow persistence. `app.keep_running` and `app.start_at_login` are separate, opt-in settings. `app.on_last_window_close = "menu_bar"` keeps the desktop resident when its menu item is enabled. Desktop status/popover, Daemon menu, and palette **Daemon: Status / Start Daemon / Stop Daemon / Restart Daemon** expose controls. UI reconnect reads journals; daemon restart respawns terminal shells in cwd and resumes supported structured chats using stored provider session IDs; interrupted turns fail/cancel and pending approvals expire. `hutan restart <id>` resumes stopped/failed chats where supported. Sources: [design lifecycle](../design.md#daemon-lifecycle), [agents restore](../agents.md#journal-and-restore), [README terminals](../../README.md#what-works-today).

**Friction / proposal.** The current menu item belongs to the desktop; [M6-D](../briefs/M6-D.md) explicitly identifies invisible background daemon operation after desktop quit. **M6-D covers** handoff of the icon to the daemon. **[INFERENCE]** A reconnect/recovery summary should say “still running,” “shell respawned,” “agent resumed,” “turn interrupted,” or “resume failed,” with relevant Retry/Open actions. Avoid a generic “restored” message that implies tests or dev servers survived daemon death. Live PTY handoff is a vision target, not verified delivered behavior.

### J9. Switch projects and recover a useful older conversation

**Comparables.** Codex groups threads by project and reuses CLI history; Zed's sidebar groups threads across projects; Conductor archives/restores workspaces; Cursor documents transcript search. Their nouns are not interchangeable.

**Hutan today.** `⌘O` → recent project/Open Folder; `⌘J` → every workspace, project, session, including hidden ones; `⌘K` → **Workspace: Go to Home**, **Workspace: New Workspace…**, sidebar organization/sort/hide commands. Projects represent repository identity, including linked worktrees; workspaces collect projects. Switching parks/restores the container's layout; inactive terminal views detach, not their daemon processes. `⌘J` query `?words`, **History: Search History…**, or **Panel: Open History** accesses opt-in search; Enable indexing is explicit. Filters cover source/role/date/project; hits open session/block, reveal transcript, or use an external harness resume command where available. `hutan index enable`, `hutan search "words"`, `hutan ws ls`, and `hutan project ls` are CLI routes. Sources: [design projects/history](../design.md#projects-and-workspaces-m12-b-rewritten-by-m18-b), [assistant indexing](../assistant.md#indexing-of-chats).

**Friction / proposal [INFERENCE].** Already a rich implementation, but the README's “one workspace per project” is obsolete relative to the project/workspace hierarchy. Name project, checkout/worktree, task, and session consistently in pickers and documentation. Keep history opt-in and explain that Hutan history before indexing was enabled is not backfilled. Distinguish focusing a live Hutan conversation from launching a new terminal to resume an external one. K-1 moves Jump to `⌘P`; update all teaching surfaces together.

### J10. Correct a running agent without losing the next instruction

**Comparables.** Cursor explicitly supports queued and immediate follow-ups; Zed queues messages and gates steering to integrations that support it; Claude Code Desktop accepts a correction at the next action boundary.

**Hutan today.** **Agent: Interrupt Turn** / `⌘.` stops the current turn. [`chat/view.rs`](../../crates/desktop/src/workbench/chat/view.rs) documents the running gate as interrupt offered, sending unavailable; [`daemon/chat.rs`](../../crates/daemon/src/chat.rs) refuses another send with “a turn is already in progress; wait for it or interrupt it.” There is no evidence here of a durable user-message queue.

**Friction / proposal [INFERENCE].** Add a bounded daemon-owned **send after current turn** queue, visibly editable/cancellable and journaled only on dispatch, so a user does not have to interrupt useful work to preserve a follow-up. Native steering should remain capability-gated and separate from interrupt; do not simulate it by racing concurrent sends into harnesses.

## 4. Prioritized gaps and architecture-fit proposals

**All prioritization and effort are [INFERENCE].** Impact: 1 = occasional convenience, 5 = central daily journey blocked/confusing. Effort: 1 = local copy/presentation change; 2 = one surface using existing APIs; 3 = cross-client/service feature; 4 = adapter/protocol/state changes; 5 = substantial new subsystem. “Impact × effort” gives both dimensions, not a severity multiplication that rewards expensive work. P0 = immediate user-requested adoption/trust blockers; P1 = next complete daily-workflow improvements; P2 = later breadth. This is not a security severity rating.

## 6. Documentation contradictions that affect trust

These are directly observable differences between the inspected documents, not claims that the implementation is broken:

1. **README status and packaging:** its opening status still calls background/menu/Dock work in progress, while detailed design documents M6-C and D-2; the bundle section says launch agent registration and native notifications are not implemented, despite the README's own Notifications feature row and later design. Replace milestone-era blanket text with accurate delivered versus in-flight capabilities.
2. **README project model:** “one workspace per project” predates [orchestration's](../orchestration.md#projects-and-workspaces) automatic projects plus user workspaces. The UI now titles the sessions sidebar Projects. Terminology matters when a user thinks a worktree is a new project.
3. **Attachments:** [assistant Attachments/Permissions](../assistant.md#attachments) includes older “only direct and assistant” / “Codex takes none” text alongside later ACP text attachment support. [agents Limits](../agents.md#limits) says text-only; R-1 will deliberately supersede this. Document a small backend × text/file/image capability table rather than another blanket promise.
4. **Assistant authority:** the opening assistant definition describes provider chat with no tools, whereas Backends documents read-only OMP/Claude/Codex tools. Clarify that direct providers have no tools and harness assistants have the backend's enforced read-only model; attachment permission is not the same as harness tool permission.
5. **History:** agents Limits says chat journals are not wired into the index; assistant's Indexing of chats says all chat journals are fed when history is enabled. Resolve against implementation before teaching a guaranteed search journey. This report does not certify which statement is current at runtime.
6. **Close semantics:** design principle “closing a window detaches” is qualified by the later default last-window-close = quit, with background/confirmation rules. Teach tab detach, resident menu-bar mode, quit, daemon restart, and host restart separately.
7. **Approval keys:** the keyboard table's focused-card `⌘↩`/Escape and chat page's empty-composer `1`–`4` have different targets. They may both be valid, but presenting them without focus/oldest-request context is unsafe instruction. Verify and publish one contextual explanation.
8. **No new-key premature promises:** current `actions.rs` still binds `⌘K`, `⌘J` Jump, `⌘⌥J` bottom dock. K-1's future default must be labeled until integrated; avoid mixing pre- and post-K-1 tables in a single help surface.
