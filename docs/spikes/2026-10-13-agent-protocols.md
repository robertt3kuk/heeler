Optional message IDs are not guaranteed; partial tool-call updates need merging.
- ACP v1 `session/prompt` stays outstanding until its response contains `stopReason`; do not synthesize completion from the last message chunk. Codex's early `turn/start` response and later `turn/completed` require a different adapter state machine.
- ACP fs capabilities gate agent→client `fs/read_text_file`, `fs/write_text_file`; terminal capability gates **all** `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill`, `terminal/release`. This probe advertised fs=false and terminal=false, so these client services were not exercised. Hutan can expose daemon-owned FS/terminal services to compatible ACP agents; capabilities do not imply every agent delegates every operation.
- Codex executes commands internally and exposes command/process control APIs and item output; those PTYs are not automatically Hutan-owned. ACP terminal delegation is a separate explicit execution path. ACP diffs carry `path/oldText/newText`; Codex file-change patches and aggregate turn diff are different representations. ACP usage may describe context/cost, not Codex-equivalent per-turn token totals.

## Recommended adapter strategy and resume semantics
1. Daemon owns independent `CodexAdapter` and `AcpV1Adapter`, subprocess/transport lifetime, request-ID maps, session records and normalized event journal; GPUI/CLI consume versioned Hutan IPC, not either vendor schema. Start with installed/version-pinned Codex stdio and generated schemas; keep experimental APIs opt-in. ACP expands multi-agent compatibility without discarding Codex-specific behavior. ACP protocol v2 is **draft**, not required merely because SDK is 2.x.
2. `AgentEvent` envelope needs local session/turn/item IDs plus provider IDs, protocol/agent version, sequence, timestamp, replay/live marker and retained opaque provider payload. Events: message start/delta/end (role, phase, text/image/resource blocks); tool start/patch/end (name/kind/raw args/output/status); output/terminal references; file diffs (patch **or** before/after); permission requested/resolved (request ID, tool identity, original options/scope and chosen result); plan snapshot/delta; usage (optional token/context/cost fields with units/scope); session metadata/config/model/capabilities; turn completion/error/cancellation; durable resume locator. Never equate absence with zero usage or flatten vendor decisions into unconditional allow/deny.
3. Pending permissions belong to daemon state and must survive a GUI disconnect while the agent remains connected. Store provider request ID + options; only answer after an explicit decision, respect actual offered options, and expire/cancel pending approvals when the turn resolves. Keep transport reads active during approvals and long-lived ACP prompt requests.
4. Codex `thread/resume(threadId)` reopens/subscribes and returns reconstructed `thread.turns`; `thread/read` can inspect without resuming and `thread/fork` creates a new ID. **Exercised after process restart**: same completed thread and model restored. This legacy-history resume returned only user/commentary/final messages, **omitted the commandExecution item**, and reassigned message IDs to `item-1/2/3`; durable Hutan journaling must not assume replay preserves all live tool records or item IDs.
5. ACP v1 `session/load(sessionId,cwd,mcpServers)` is capability-gated and replays history via `session/update` **before** responding; `session/resume` is separately advertised and restores without replay. This agent advertises both; actual recovery [UNVERIFIED]. Distinguish replay from live events and persist protocol-specific session IDs, cwd, model/config and backend storage context. Never assume Codex thread IDs and ACP session IDs are interchangeable across adapters/homes.
