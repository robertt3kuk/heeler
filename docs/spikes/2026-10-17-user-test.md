# Hutan hands-on user test — 2026-10-17

## Executive result

Tested the supplied release bundle of `b372ffa`, protocol **0.27**, not the installed Hutan. The terminal/block substrate, isolated worktrees, task delivery states, local commit/merge, presets, Resources, history privacy gate, and visual themes are useful already. The strongest observed failure is **desktop terminal views remaining attached to dead terminals after a daemon restart, while the daemon has successfully respawned their shells**. The strongest usability hazards are the launcher's immediately billable default path, automatic hook installation being on by default even with a custom home, and a Command field that looks like a shell command but executes argv instead.

**No confirmed application-wide blocker. Four major findings: F1–F4.** This is not an exhaustive mouse/accessibility certification: the specific uncompleted UI checks are listed below, rather than marked passing.

### Important execution incident

The no-paid-turn constraint was accidentally breached once during keyboard-only launcher exploration. Starting from the default **Agent chat / OMP / main checkout / focused Prompt**, navigation intended to reach Plain terminal instead reached the Agent row, selected Codex, and pasted `Plain keyboard launch` into Prompt. The pre-submit screenshot **58-plain-title.png** clearly shows **Agent chat / Codex / GPT-6.1-Sol / Prompt**, not Plain terminal. `⌘↩` immediately started the turn. This is a tester navigation error and a launcher footgun, **not evidence that a correctly selected Plain terminal secretly launches Codex**.

The session was interrupted and stopped as soon as noticed. By then its turn had completed in **9.5 s**; the UI showed approximately **70.0k total tokens**, **69.8k input**, **53.2k cached input**, and **173 output**. It read the scratch repository's README and asked for clarification; no file edit was observed. Session: `01M54K1F55TWKZR0CBWKJCK6Z1`; harness session: `01a14930-bcd6-7031-9370-3a3e42d9c5e1`. The integrator was notified and acknowledged the incident. No further agent turn was launched. A subsequently inspected composer draft was not sent. Any harness-owned transcript in the real Codex home was left alone; its location was not inspected. **Zero model usage or complete harness-write isolation cannot be claimed.**

### Input and timing limitations

The active input source was **Russian** (`com.apple.keylayout.Russian`, observed with the Text Input Source API). AppleScript ASCII `keystroke` produced repeated Cyrillic characters and unreliable character-based shortcuts. **This is a harness limitation, not a Hutan text-input bug.** Physical `key code` shortcuts were used thereafter. Paste used a temporary clipboard value with restoration of all saved pasteboard items.

Coordinate `System Events` clicks often returned a window without changing the intended custom control; one native tiling attempt returned **“osascript is not allowed assistive access” (-25211)** after about **10.2 s**. These failures are not proof that normal mouse clicks fail. The native `⌘⇧G` retry also consumed an old restored clipboard value (`hutan`) rather than the supplied scratch path: the reversible-paste helper and native event delivery remain a confound. Palette/Jump paste failures likewise are recorded as **unverified input-delivery issues**, not confirmed app defects.

The screen was unlocked when checked (`IOConsoleLocked = No`). A performance worker later reported that its short-lived benchmark windows also needed foreground focus. Each test event activated this test pid first, but concurrent focus competition is another reason not to overinterpret failed UI input.

CLI timings are subprocess wall time, not internal service profiling. UI timing includes deliberate settling and AppleScript overhead: later key actions typically took **0.69–0.74 s**, including **0.55 s** of explicit delay. Table timings marked `script` are interaction time excluding the potentially long gaps spent inspecting evidence; they are **not human completion-time benchmarks or frame-latency measurements**. Competitor timings below are recommended experience targets, not measured competitor results.

## 3. Findings

Severity describes observed user impact, not a security exploit rating. Recommended designs and probable causes are marked [INFERENCE]. Harness-limited checks are not silently promoted into product bugs.

### F1 — Respawned shells exist, but open desktop terminals stay dead

**Severity: major. Area: daemon reconnect / terminal attachment.**

1. Open several terminal tabs/splits in the isolated app.
2. Run `hutan daemon restart --stop-sessions` with the scratch home.
3. Observe `hutan recovery`: **6 shells respawned**, explicitly “Its screen and processes did not survive.”
4. Send `printf 'HUTAN_SEARCH_MARKER_42\n'` to the respawned Home session. `history` contains the new marker and search finds it.
5. Inspect the already-open terminal, and use `ui run OpenSession` on the same session id.

**Expected:** existing views detach from old terminal ids and attach to the respawned terminals, or offer an explicit reconnect action.

**Actual:** views retain the old `HUTAN_BLOCK_OK` screen, show **“The daemon restarted; this session is gone”** and Close, and do not show the live marker. Opening the same session did not replace that stale view. Other split terminals show the same dead-session footer. The daemon itself is working.

**Evidence:** E/75-restart-summary.png, E/76-history-enabled.png, E/77-reopen-respawned-session.png, E/88-command-worktree-result.png; recorded `recovery`, `send`, `history`, `search` and OpenSession outputs. **Probable cause [INFERENCE]:** a terminal view keeps the pre-restart terminal identity instead of re-resolving the stable session id.

### F2 — Default Start path can spend model usage after keyboard navigation goes astray

**Severity: major usability footgun. Area: launcher / focus / execution consent.**

1. Open `⌘⇧T`. Default: Agent chat, OMP, main checkout, focused Prompt.
2. Attempt keyboard navigation toward Plain terminal. In the recorded exploratory sequence, Shift-Tab ×3, Tab and arrow navigation did not reliably land on the intended row as model/loading and field state varied.
3. The later sequence included Right ×2, Tab ×2 and paste `Plain keyboard launch`. Actual pre-submit state was **Codex selected and Prompt focused**, shown in screenshot 58.
4. Press `⌘↩`.

**Expected (usability recommendation):** before the first immediately billable launch, make the action unmistakable: e.g. “Start Codex · GPT-6.1-Sol in orchard/main,” with a one-time explicit confirmation or equally clear execution summary. Preserve obvious focus and do not teach count-based navigation that changes as fields load.

**Actual:** generic **Start** immediately began a real turn, with no separate confirmation. The tester's mistaken interpretation was not corrected before execution. The UI accurately showed Codex; this is **not** a wrong-backend execution bug. A subsequently visually verified Plain terminal selection worked normally.

**Evidence:** E/35-launcher-settled.png, E/38-launcher-keyboard-focus.png, E/57-next-launcher-default.png, E/58-plain-title.png, E/59-plain-start-outcome.png, E/61-resources.png; exact key scripts and interruption/stop commands in observations.json. **Probable area [INFERENCE]:** launch-kind prominence, dynamic focus order and generic submission affordance. No further agent launch was attempted after the incident.

### F3 — Fresh custom home still defaults automatic real-agent hooks on

**Severity: major consent/isolation concern. Area: onboarding / integrations.**

1. Launch the test bundle with an empty custom HUTAN_HOME.
2. Continue to Bring your agents.
3. Inspect **Install agent hooks automatically** and `ui actions` settings.

**Expected:** a sandbox/custom home should not implicitly authorize integration changes in real agent homes; users should choose such changes knowingly.

**Actual:** `integrations.auto_install = true` by default, switch on; copy says Hutan adds its hooks on each start. Real installed accounts/hooks were detected despite custom HUTAN_HOME. The test set it false and did not click Install, Uninstall or Log in. Whether this particular launch modified an existing real config was **not verified** and is not asserted. The write destination/risk is grounded in the setup's integration model; actual config mutation in this pass remains unverified.

**Evidence:** E/05-setup-look.png (Agents page), initial `ui actions` output with `integrations.auto_install = true`, scratch settings with it false, E/97-setup-safe-agents.png. **Recommendation [INFERENCE]:** opt-in installation and explicit destination/consent; document that HUTAN_HOME does not isolate external harness state.

### F4 — Command field looks shell-like but does not run shell composition

**Severity: major workflow friction. Area: launcher command execution / copy.**

1. Start → Command in the scratch Git project.
2. Enter `printf 'LAUNCHER_COMMAND_OK\n'; pwd`.
3. Choose New worktree and Start.

**Expected:** a terminal-like command field either runs that normal shell sequence, or clearly says it accepts an executable/argv only and explains how to invoke a shell.

**Actual:** the worktree is created, but the task stores argv equivalent to `printf LAUNCHER_COMMAND_OK\n; pwd`; it prints the marker, reports **“printf: missing format character”**, and exits 1. `pwd` is not run as a second command. There is no visible shell-vs-argv explanation in the form.

**Evidence:** E/86-confirmed-command.png, E/87-command-worktree-fields.png, E/88-command-worktree-result.png; task ls records failed exit 1. This is a UI semantic mismatch even if direct argv execution is deliberate. **Recommendation [INFERENCE]:** retain deliberate argv execution if desired, but label it truthfully and provide an explicit shell-command path.

### F5 — Changes toolbar clips essential integration action even at default window width

**Severity: minor. Area: Changes / responsive layout.**

1. Keep both docks visible in a 1280-point-wide window.
2. Open the worktree's Changes tab; zoom the pane without hiding docks.

**Expected:** Accept, Request changes, dirty toggle, Refresh and Merge stay reachable/readable through wrapping or overflow.

**Actual:** the single horizontal toolbar extends beyond the center pane; **Merge into main…** is cut off at the dock boundary. A half-width split is worse. No overflow affordance is visible in the captured toolbar. Mouse/scroll access beyond the clipping was not certified.

**Evidence:** E/43-worktree-diff.png; E/41-changes-dirty.png for a narrower split. **Probable cause [INFERENCE]:** non-wrapping toolbar with fixed-size actions.

### F6 — Assistant action is advertised but CLI dispatch rejects it

**Severity: minor. Area: UI automation action registry / assistant entry point.**

1. `ui actions` lists `workbench::OpenAssistant`.
2. Set `assistant.enabled true`.
3. `ui run workbench::OpenAssistant`.

**Expected:** open/focus Assistant or return a backend-setup state.

**Actual:** **not_found: unknown action** despite the listed action and enabled setting. `ui run workbench::OpenPanel --arg id=assistant` succeeds and shows the correct no-backend setup card.

**Evidence:** exact actions/set/run outputs in E/observations.json; E/71-assistant-panel.png. **Probable cause [INFERENCE]:** registry/dispatch mismatch rather than a missing Assistant panel.

### F7 — Successful Quit reports command failure

**Severity: minor. Area: CLI UI request lifecycle.**

1. Enable Keep Running through its existing action.
2. `ui run workbench::Quit`.

**Expected:** successful quit is acknowledged as success.

**Actual:** app closes and live daemon remains as intended, but CLI exits 1 with **“the window closed before it answered.”** This occurred on successful cleanup quits too. Automation may unnecessarily retry or report failure.

**Evidence:** Quit outputs in E/observations.json, followed by process/ls output proving the app closed and daemon/sessions persisted. **Probable cause [INFERENCE]:** response lifetime ends with the window before action acknowledgement.

### F8 — Settings exposes implementation vocabulary instead of user-facing guidance

**Severity: polish. Area: Settings copy / navigation.**

1. Open `⌘,` → appearance.
2. Read category names and density description.

**Expected:** human labels such as Appearance, Session List and “Compact uses smaller rows.”

**Actual:** lowercase/schema names including `panels.sessions` and `panels.inspector`; density help says **“see the density token table in docs/design.md”**; appearance help discusses older config-file key migration. It feels like an internal configuration editor rather than a polished settings sheet.

**Evidence:** E/48-settings.png, E/93-narrow-settings.png (despite its filename, window did not actually narrow). Recommendation is copy-only [INFERENCE], not a request for a second settings system.

### F9 — Rename starts at end of old text; simple paste appends

**Severity: minor. Area: sidebar rename.**

1. Pin current project and invoke Rename Active Workspace (which correctly targets the active project here).
2. Paste `Orchard review`, Return.

**Expected (native rename convention):** old name selected so typing/paste replaces it.

**Actual:** result is **orchardOrchard review**. CLI project rename corrected it afterward. Requiring Select All is workable but easy to miss.

**Evidence:** E/89-rename-project.png, E/90-sidebar-pinned-renamed.png; project ls and ws ls show the concatenated name. **Probable cause [INFERENCE]:** initial caret placement without selection.

### F10 — Time and documentation conventions make recovery/history harder to interpret

**Severity: minor. Area: CLI history / documentation.**

1. Run a new shell command, search it and inspect recovery in the same session.
2. Compare local `date` with the search row.
3. Read README's requirements/feature/status claims against the exercised UI.

**Expected:** timestamps have a consistent local-time convention or explicit zone; README accurately teaches delivered features and nouns.

**Actual:** local clock was **14:31 +0500**, recovery said **14:31**, while the new search row showed **09:31** without a UTC label. README also says one workspace per project and contains milestone-era claims about notification/login support, whereas the runtime has project containers inside named workspaces and the detailed design explains the newer lifecycle. The old audit already identified documentation drift; runtime grouping was now exercised.

**Evidence:** `date`, `search` and `recovery` outputs in this transcript/observations; E/75-restart-summary.png, E/91-workspace-sidebar.png; README lines 9, 25, 173, detailed design and the earlier audit. The native notification feature itself was not tested in this re-identified bundle.

### F11 — Launcher retains another backend's installation error

**Severity: minor. Area: launcher / backend readiness.**

1. Open Start and navigate through the Agent selector, including the unavailable Claude Code adapter.

## 4. Top ten fixes ranked by user impact

All proposed designs are recommendations [INFERENCE]; rank is user impact, not a claim that every item is equally proven.

1. **Reattach open terminal views after daemon epoch/terminal-id changes (F1).** Stable session id should resolve to the new terminal; stale screens need a working Reconnect action.
2. **Make the first billable Start unmistakable (F2).** Backend/model/checkout in the submit label or final summary, stable keyboard focus, and a first-use confirmation. Do not add confirmation to every routine shell launch.

5. **Keep review/integration actions reachable at realistic pane widths (F5).** Wrap or overflow the Changes toolbar; preserve dirty/committed scope explanation.
