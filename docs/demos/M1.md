# M1 demo: daemon + CLI terminals

Manual checklist for the M1 exit demo (`docs/roadmap.md` § M1): one session, two attached clients, detach/reattach, resize, `ls --json`, stop, clean shutdown, and bounded memory under heavy output. Everything runs against a throw-away daemon, so it never touches your real `~/Library/Application Support/Staffy`.

Needs two terminal windows (A and B) on the same Mac, both at least 100×30 so step 8 has room to grow. The coding agent is `omp`; if it is not installed use `vim` (any full-screen program works the same).

## 0. Setup (once, in both A and B)

```sh
cd <repo>
cargo build --release -p staffy-cli -p staffy-daemon      # builds target/release/staffy and staffyd
export PATH="$PWD/target/release:$PATH"
export STAFFY_HOME="$(mktemp -d /tmp/staffy-demo.XXXXXX)"  # same value in A and B: copy it from A
echo "$STAFFY_HOME"
```

Expected: `staffy --version` prints `staffy 0.1.0`. In B, paste the `STAFFY_HOME` printed in A (`export STAFFY_HOME=/tmp/staffy-demo.…`) so both windows talk to the same daemon. The socket is `$STAFFY_HOME/staffyd.sock`.

## 1. Start the daemon (A)

```sh
staffy daemon start
```

Expected: `started: staffyd 0.1.0 (protocol 0.1) pid <pid>, up 0s, 0 session(s), 1 client(s)` (the one client is this command itself) followed by the socket and epoch lines. Running it again prints `already running: …` with the same pid and epoch (idempotent).

## 2. Start a session and attach (A)

```sh
staffy new --attach --title demo -- omp        # or: staffy new --attach --title demo -- vim
```

Expected:
- The line `session <ULID> terminal 1` is printed, then the window switches to the alternate screen and shows the program's own UI (omp's prompt, or vim's start page). Typing goes to the program: keys, arrow keys, and ctrl+c reach it unmodified (ctrl+c does **not** kill `staffy`).
- Write down the session id (it is also in step 3).

## 3. Inspect from the other window (B)

```sh
staffy ls --json
staffy ls
```

Expected:
- JSON: `{"sessions":[{"id":"<ULID>","title":"demo","state":{"state":"running"},"terminal_id":1,"command":["omp"],"cwd":"<A's directory>",…}],"seq":<n>}`.
- Table: columns `ID TERMINAL STATE TITLE CWD AGE`, one row with `t:1`, `running`, `demo`.
- `staffy daemon status` shows `1 session(s), 2 client(s)`: A's attach plus the status command itself (B's other commands connect and leave).

## 4. Second client on the same session (B)

```sh
staffy attach demo            # also valid: the full id, a unique id prefix of ≥ 4 chars, or t:1
```

Expected:
- B shows the **same screen** as A at once, in B's window.
- Type something in B: it appears in A too, and the other way round. Both windows follow every change (two clients attached, one terminal).
- `staffy daemon status` (run from a third window, or after detaching) shows `3 client(s)` while A and B are attached: the two attaches plus the status command itself.
- An ambiguous target is refused: with a second session titled `demo`, `staffy attach demo` prints the candidate ids on stderr and exits 2.

## 5. Detach and reattach (B)

Press **ctrl+\\** then **d** in B.

Expected:
- B leaves the alternate screen, the shell prompt is back with its earlier content intact, and the last line printed is `[detached from <ULID>]`; exit status 0 (`echo $?`).
- A is unaffected and keeps running the program.
- Reattach: `staffy attach demo`. B shows the current screen again, including anything typed in A in the meantime.

Sending a literal ctrl+\\ to the program: press ctrl+\\ twice. ctrl+\\ followed by any other key forwards both keys.

## 6. Send input without attaching (B)

```sh
staffy send demo 'hello from B' --enter     # for vim, first press `i` in A
staffy history demo --lines 20
```

Expected: the text appears in A and B (the program receives it as typing, `--enter` presses return). `history` prints the scrollback and the current screen as plain text, oldest line first.

## 7. Heavy output stays bounded (B)

```sh
staffy new --title flood -- sh -c 'seq 1 10000000; exec cat'
staffy attach flood
```

Expected: the numbers scroll; the window stays responsive (type a few characters, they echo). Detach with ctrl+\\ d. Then:

```sh
staffy history flood --lines 5
ps -o rss= -p "$(staffy daemon status --json | sed 's/.*"pid":\([0-9]*\).*/\1/')"
```

Expected: `history` ends with `10000000`; the daemon's resident memory stays in the tens of MB (scrollback is capped at 10 000 lines). The automated 200 MB version of this step is the bench:

```sh
cargo run --release -p staffy-daemon --example flood
```

Expected: one `flood: …` summary line, exit status 0: `silent_renders_after_snapshot=0`, `status_p99` < 50 ms, `peak_rss` < 120 MiB, `final_screen=match`.

## 8. Resize (A)

Make window A bigger or smaller (drag the corner), then in A's attached program check the size:

- omp / vim redraw to the new size (vim: `:echo &columns &lines`).
- For a plain shell session: `staffy new --attach -- sh`, then `stty size` prints `<rows> <cols>` of the window; resize the window and run it again: the new size is shown.

Expected: the program always sees the size of the window that resized or attached most recently (one PTY, last writer wins). A second attached client keeps showing the program clipped or padded to its own window.

## 9. Stop a session (B)

```sh
staffy stop demo
staffy ls
```

Expected:
- A leaves the alternate screen and prints `[session stopped]` (exit 0). A program that exits by itself prints `[session exited with code N]` instead.
- `staffy ls` shows `demo` with state `stopped`. `staffy attach demo` flashes its final screen, prints `[session stopped]` with the restart/history hint, and exits 0; `staffy history demo` still prints its last output; `staffy restart demo` starts it again with a new terminal id (`session <ULID> terminal <n>`).
- `staffy send demo x` on a stopped session fails with exit status 1.

## 10. Shut down (B)

```sh
staffy daemon stop                    # refused while sessions run: exit 1, "invalid_state"
staffy daemon stop --stop-sessions
staffy daemon status                  # exit 3, "cannot connect to staffyd …"
ls "$STAFFY_HOME"                     # no staffyd.sock any more
```

Expected: all sessions end (their processes are gone: `pgrep -f 'omp|vim'` finds nothing from this demo), the socket file is removed, and a later `staffy daemon start` starts a fresh daemon with a new epoch.

## Clean up

```sh
rm -rf "$STAFFY_HOME"
```

## Failure checklist

- Terminal left in a strange state after a crash: `reset`. `staffy attach` restores the terminal on detach, session end, errors, SIGTERM, SIGHUP, and panics; if it did not, that is a bug to report.
- `staffy: cannot connect to staffyd …` (exit 3): wrong or missing `STAFFY_HOME` in this window, or the daemon is not running (`staffy daemon start`).
- Daemon log: `$STAFFY_HOME/logs/staffyd.log`.
