## Contract
- **Catalog and layout** (desktop → daemon): `ui.publish {actions: [{id, title, args_schema?}], settings: [{namespace, key, type, doc, layers}], layout: LayoutSummary}` on connect and whenever they change (debounced 250 ms). `id` = the GPUI action name (`workbench::SplitRight`), plus parameterized actions the palette offers (apply preset X, open panel Y, focus session Z). `LayoutSummary {window_id, workspace_id?, preset, docks: [{position, visible, panels, active}], panes: tree of {pane_id, items: [{kind: terminal|chat|panel, session_id?, title}], active}, focused, zoomed, appearance}`.
- **Requests**: `ui.actions {window_id?}`, `ui.layout {window_id?}` → cached data; `ui.run {window_id?, action, args?}` → routed as event `ui.command {request_id, action, args}` to that desktop (default: the most recently focused window) → desktop replies `ui.command_result {request_id, ok | error}` → the caller gets it (timeout 5 s → `internal` with "the window did not answer"). `ui.set_setting {namespace, key, value, layer}` → executed the same way (desktop validates with the schema, writes the TOML layer, hot reload applies). Errors: no desktop → `invalid_state`; unknown action/key → `not_found`; bad args → `bad_request`.
- **Origin**: `ClientInfo.origin?: {session_id}`; the CLI and `hutan mcp` set it from `HUTAN_SESSION_ID`. The daemon verifies the session exists and is live, else ignores the claim (logs it).
- **Policy**: `daemon.toml [control] agents = "ask" | "allow" | "read_only"` (default `ask`), `mcp = true`. Every request is classified read/mutate in one table in the router (unit-tested exhaustively: a new request kind must be classified or the build/test fails). For agent-originated mutations: `ask` → approval kind `control` (title: plain description of the request incl. the target session/action; options `allow_once`, `allow_session`, `deny`; resolved through the existing approval machinery, visible in `hutan approvals`, the desktop approval UI and native notifications; `allow_session` remembered per origin session); `read_only` → `forbidden`; `allow` → run. All agent-originated mutations are written to the approvals audit table with the decision. Requests that change `[control]` or credentials are never allowed from agents.
- **CLI**: `hutan ui actions [--json]`, `hutan ui layout [--json]`, `hutan ui run <action> [--arg k=v]…`, `hutan ui set <namespace.key> <value> [--layer user|workspace|project]`; `hutan help agent` (compact guide for agents: what they can do, that mutations may wait for approval).
- **MCP server** `hutan mcp` (stdio, MCP 2025-06-18 or the newest stable the chosen crate supports; `rmcp` if it builds offline from the cache or a small hand-rolled JSON-RPC server): tools generated from a declarative table mapping to daemon requests — sessions (list, create, send text, history tail, stop, restart, rename), chats (create with agent, send, log), approvals (list — not respond), tasks (add, list, start, done, cancel, reset), worktrees (new, list, rm), workspaces/projects (list, create, assign, open), notifications (list), search (history), ui (actions, layout, run, set_setting). Descriptions written for models; a mutation's result says when it waited for or was denied approval.
- **Wiring**: harness/Codex sessions Hutan starts get `hutan mcp` as an MCP server when `[control] mcp = true` — implement the hook in the chat manager in a way M8-A's ACP path can call (a function returning the MCP server spec); for Codex add `-c mcp_servers.hutan.command=…`. `hutan integration install omp|claude|codex --mcp` adds the server to the user's own configs (marked entries, backup, uninstall) — only on that explicit command.
