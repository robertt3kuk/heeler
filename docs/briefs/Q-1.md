## Contract
- **Question** model next to approvals: `QuestionId`, session, turn, `title`, `prompt` (markdown), `fields: [{id, label, kind: text | multiline | choice{options, multi} | number | boolean | secret?, required, default?}]` (mapped from the provider's JSON-schema subset: string/enum/number/boolean; unknown shapes → one free-text field + the raw schema shown), `requested_at`, `expires` (turn end / process exit / daemon restart, like approvals), provenance `decided_by` on answer.
- Requests: `question.list`, `question.answer { question_id, values | decline | cancel }`; events `agent.question_requested`, `agent.question_resolved` in the chat journal.
- Adapters reply with the real provider shape: Codex `requestUserInput` answers / MCP elicitation `accept {content}` / `decline` / `cancel`; ACP: only what a harness actually sends (if none do, keep refusing but with a precise notice, documented).
- `secret` fields (if a schema marks a password/token) are never journaled or logged — the journal records "answered (secret)".
- Desktop: a **question card** in the chat (form controls built from fields, Submit ⌘↩, Decline, Cancel); counts in attention/Needs you/badge like approvals (`AttentionKind::Question`); a native notification intent `question_required` (M6-B) with "Open" only; Inspector → Approvals tab becomes "Requests" listing both.
- CLI: `hutan questions`, `hutan answer <id> field=value … | --decline | --cancel`.
- Keyboard safety: the `1–4` approval shortcut never answers a question; focused-card keys only.
